# ADR-0008: 쿼리 complexity / depth 제한

## 상태

채택 (Accepted)

## 맥락

REST 와 달리 GraphQL 은 클라이언트가 쿼리의 모양을 정한다. 이는 유연하지만, 악의적이거나
실수로 만든 쿼리 하나가 게이트웨이와 그 뒤의 9개 downstream 을 한꺼번에 끌어내릴 수 있다는
뜻이다.

두 가지 위험한 패턴이 있다.

- **깊은 중첩** — 조인 필드가 서로를 참조하는 구조에서 쿼리를 깊게 중첩하면, 한 쿼리가
  지수적으로 많은 resolver 호출로 펼쳐질 수 있다.
- **넓은 필드 폭증** — 한 레벨에 필드를 잔뜩 나열하거나 같은 조인을 여러 alias 로 반복하면,
  중첩이 깊지 않아도 호출 수가 폭증한다.

이런 쿼리는 게이트웨이 자원과 downstream 자원을 동시에 소진시키는 DoS 가 된다.

## 결정

쿼리를 **실행하기 전에** 정적으로 검사해, 비용이 한계를 넘으면 거부한다. graphql-java 의
instrumentation 두 개를 등록한다.

- **`MaxQueryDepthInstrumentation`** — 쿼리 선택 트리의 최대 중첩 깊이를 제한한다. 깊은
  중첩을 막는다. 기본 한계 15.
- **`MaxQueryComplexityInstrumentation`** — 필드 수에 가중치를 합산한 복잡도 비용을
  제한한다. 넓게 퍼지는 쿼리를 막는다. 기본 한계 200.

instrumentation 은 쿼리 파싱 / 검증 단계에서 동작하므로, 한계를 넘는 쿼리는 resolver 가
한 번도 호출되지 않고 거부된다 — downstream 호출 0.

한계값은 `gateway.query-guard.max-depth` / `max-complexity` 로 조정한다. 기본값은 게이트웨이
schema 의 정상 쿼리(조인 2~3단계)를 넉넉히 허용하면서 명백히 비정상인 쿼리는 거르는 선이다.
실제 클라이언트 쿼리 모양을 관측해 조정한다.

### 보조 장치 — 페이지 크기 제한

목록 쿼리의 `first` 인자(한 페이지 항목 수)도 안전 범위(1~100)로 자른다. 클라이언트가
`first: 100000` 같은 값을 보내도 100으로 깎인다. complexity 제한과 함께, 거대한 페이지로
downstream 을 끌어가는 것을 막는 1차 방어다.

## 결과

- 깊거나 넓은 쿼리가 실행 전에 거부되어, 게이트웨이와 downstream 자원이 보호된다.
- 한계를 넘은 쿼리는 resolver 를 한 번도 호출하지 않으므로 downstream 부하가 0이다.
- 거부된 쿼리는 GraphQL `errors` 로 응답한다(ADR-0005 의 변환을 거친다).
- 단점: 정적 complexity 계산은 실제 비용의 근사치다. 어떤 필드는 가볍고 어떤 필드는
  무겁지만(조인 여부 등) 가중치가 같게 잡힐 수 있다. 정밀하게 하려면 필드별 complexity
  가중치를 schema 에 부여해야 하는데, 지금은 균일 가중치로 시작하고 필요 시 정교화한다.
- 한계값이 너무 낮으면 정상 쿼리가 거부된다. 클라이언트 쿼리 패턴을 보고 조정해야 한다.
