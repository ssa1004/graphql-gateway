# ADR-0007: resolver 캐싱 — Caffeine 과 stampede 회피

## 상태

채택 (Accepted)

## 맥락

게이트웨이가 같은 데이터를 짧은 시간 안에 반복 조회하는 경우가 있다.

- 인기 있는 사용자 / 상품이 여러 클라이언트의 쿼리에 동시에 등장한다.
- 한 화면이 같은 사용자를 여러 경로로 참조한다(주문자이면서 동시에 다른 거래의 구매자 등).

DataLoader(ADR-0002)는 **한 요청 안**의 중복 키를 합쳐 준다. 하지만 서로 다른 요청 사이,
그리고 짧은 시간 간격을 두고 들어오는 같은 조회는 매번 downstream 을 친다.

## 결정

비교적 안정적인(자주 안 바뀌는) downstream 응답에 한해, 게이트웨이에 단기 캐시를 둔다.
구현은 Caffeine 이다.

캐시 대상은 보수적으로 고른다.

- **캐시함** — 사용자 프로필처럼 분 단위로는 거의 안 바뀌는 데이터.
- **캐시 안 함** — 거래 상태, GPU job 상태, 보안 알림처럼 실시간성이 중요한 데이터.
  이런 데이터를 캐시하면 클라이언트가 낡은 상태를 보게 된다.

캐시 TTL 은 짧게(수십 초~수 분) 둔다. 게이트웨이 캐시는 정확성보다 부하 완화가 목적이고,
TTL 이 길면 downstream 이 갱신돼도 게이트웨이가 낡은 값을 오래 들고 있게 된다.

### cache stampede 회피

캐시 항목이 만료된 직후, 같은 키에 대한 요청이 동시에 여러 개 들어오면, 모두 캐시 미스가
되어 한꺼번에 downstream 을 친다(stampede / thundering herd). 만료 순간 downstream 에 부하가
몰린다.

Caffeine 의 로딩 캐시(`AsyncLoadingCache` / `LoadingCache`)는 같은 키에 대한 동시 로드를
하나로 합쳐 준다 — 한 키가 만료돼 여러 요청이 들어와도 로드 함수는 한 번만 실행되고, 나머지
요청은 그 결과를 기다린다. 이 동작으로 stampede 를 막는다.

## 결과

- 안정적인 데이터의 반복 조회에서 downstream 호출이 준다.
- 로딩 캐시 덕에 만료 순간에도 downstream 호출이 키당 1회로 합쳐진다.
- 단점: 캐시된 데이터는 TTL 만큼 낡을 수 있다. 그래서 실시간성이 중요한 타입은 캐시하지
  않는다. 캐시 대상 선정이 곧 정확성과 부하의 절충점이다.
- 단점: 게이트웨이가 여러 인스턴스로 뜨면 캐시도 인스턴스별로 따로 존재한다(로컬 캐시).
  인스턴스 간 캐시 일관성은 보장하지 않는다. 짧은 TTL 로 이 불일치 창을 줄인다. 더 강한
  일관성이 필요해지면 Redis 같은 공유 캐시로 옮기는 것을 검토한다 — 지금 규모에서는 로컬
  캐시로 충분하다.

## 용어 풀이 (쉽게)

- **캐시 / Caffeine** — 한 번 가져온 답을 잠깐 손 가까운 서랍에 베껴 두고, 같은 걸 또 물으면 멀리 안 가고 서랍에서 바로 꺼내 주는 것. Caffeine은 그 서랍을 서버 메모리 안에 두는 자바용 캐시 라이브러리.
- **TTL (Time To Live, 유효기간)** — 캐시에 베껴 둔 답을 "이 시간까지만 믿고 쓴다"는 만료 시계. 지나면 버리고 새로 가져오는데, 짧으면 덜 낡지만 자주 가져오고 길면 빠르지만 오래된 값을 들고 있을 위험이 있다.
- **cache stampede / thundering herd (떼몰림)** — 캐시 유효기간이 끝나는 그 순간, 여러 요청이 동시에 "없네" 하며 원본 서버로 한꺼번에 우르르 몰려 짓밟는 현상. 셔터 올라가는 순간 손님이 한꺼번에 들이닥치는 셈.
- **로딩 캐시 (LoadingCache)** — 같은 키가 비어 여러 요청이 동시에 들어와도 실제 조회는 한 번만 하고 나머지는 그 결과를 같이 기다리게 묶어 주는 캐시. 한 명만 사 오고 줄 선 사람들은 그걸 나눠 받아 떼몰림을 막는다.
